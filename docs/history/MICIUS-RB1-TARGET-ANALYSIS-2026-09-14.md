# MICIUS RB1 目标 GEMV 差异分析 · 2026-09-14

本报告分析已完成的 `rb1-windows.yHDdqW` 批次。当前未发现旧 Q8 A 没有、而 r1 Q8 双行热内核独有的显著额外开销或需要定点修复的运行时缺陷。这个判断来自同批计时、实际编译命令和当前 EXE 的关键循环，而非历史 r1 的 2% 门槛。

已能解释的主要差异是：旧 A 省略运行时检查；r1 prepared 复用 activation 准备，但保留权重转换；旧 B 物化 F64 权重并删除热循环权重转换，代价随工作集扩大而显现。小矩阵、模型形状与完整 decode 必须继续分开。

## 1. 本批有效范围

- 用户目标 Windows、逻辑 CPU 4、单线程；Clang 22.1.8，O3/native，AVX2，显式 `-fno-fast-math -ffp-contract=off`。OFF 为禁 LTO，ON 为 ThinLTO；这两个标签不是 r1 prepared 功能开关。各二进制都包含严格 F32 与 prepared 对照。
- 实际命令同时固定 `-mno-avx512f -mprefer-vector-width=256 -funroll-loops -falign-functions=32 -falign-loops=32 -fno-omit-frame-pointer -fno-stack-protector`。共同调用循环 `timer.cpp` 两侧都单独以 `-fno-lto` 编译。核对了复用对象的旧命令与本批重编译/链接记录，未以 CMakeCache 或 banner 代替它们。
- 六种形状来自已知 SmolLM2 GGUF 元数据，权重、scale、activation 为统一合成数据。32 层、H=960、I=2560、KV=320；LM head 使用 tied embedding 的 49152×960 形状。没有运行真实模型 forward 或 decode。
- 四轮全部保留；LTO 顺序 OFF/ON、ON/OFF、OFF/ON、ON/OFF；入口顺序按预先规定的正向、反向、半轮换、反向半轮换。一次校准后的迭代数在两侧及四轮复用。
- 每个计时前有三次入口 warmup。准备、检查和消费按下面各入口定义计入；计时外输出与冻结参考逐位比较。有效缓冲 64 B 对齐；双消费使用同一 activation、两个不同权重矩阵。
- 算术保持 `(double(input) * double(raw_q8)) * double(scale)`、每输出行四条向量累加链、既定规约树和最终 F32 转换；B 预展开的是精确整数值，没有预乘 scale。独立冻结参考未修改，诊断适配差异保存在随包源码证据中。
- 本批 8 个 CSV、608 条样本齐全，命令退出码均为 0；全部样本 CPU 起止均为 4、MXCSR 控制位为 8064，输入 hash、输出与相应入口一致。正样本时间区间为 0.0744385–0.3217009 s，没有把零时长或失败探针纳入样本。
- OFF/ON 各自新增验证：192 个形状 × 14 入口 = 2688 次逐位检查；负例、重复调用计数、校准策略自测均 PASS。它们不是历史旧实验 200 组、r1 252 组，也不是失落工具截图的 200×9。

原报告 CRC 和 259 条清单核对通过；两侧各 24 条当前源码清单记录与随包源码对应，EXE 摘要对应。历史 r1 数值、真实模型和目标审查结论继续复用；本轮未修改正式数值路径，也未重跑未变模块的全套验收。

## 2. 时间口径与统计

单消费入口计为 ns/GEMV；双消费计为 ns/pair，pair 内两个完整 GEMV。组件入口不是 GEMV：prepare/scan 按一次长度 C 的输入操作，expand 按一个 R×C 权重数组操作。有效元素与 block 的归一化在 `tables/medians-and-normalized.csv` 中保存；组件的 GEMV 归一化留空。

下面绝对时间表单位统一为 **μs/operation**，取四轮中位数。增益表为 `median(同轮 A 时间 / B 时间 − 1) × 100%`，括号是 B 获胜轮数。该配对统计不等于“两个中位数相除”，也不是置信区间。四轮的全部原值保存在 `analysis.json` 与 CSV 中；没有删除第三轮 LM head 较慢的 F32 样本或追加样本追求正收益。

| 入口 | 计时内工作 |
| --- | --- |
| old_q8_a / old_f64_b | 旧 A/B 算术内核与共同适配调用；前提检查在外，B 的权重展开在外 |
| r1_f32_kernel / r1_prepared_kernel | 由 r1 源码最小生成的诊断内核；省去验证、尾部及输出检查，prepared 输入在外准备 |
| r1_f32_prevalidated | 实际 r1 F32 入口：参数、activation 有限值、输出检查；scale 走私有预验证边界 |
| r1_f32_checked | 上一项再加 block scale 检查 |
| r1_prepared_consume | 实际 prepared 行入口：视图、范围、MXCSR、输出检查；输入在外准备 |
| r1_prepared_total | 实际准备一次 + 实际 prepared 入口一次 |
| r1_f32_dual / r1_prepared_dual | 实际 F32 两次消费 / 实际准备一次加两次消费 |
| prepare_only / scan_only | 实际准备函数 / 独立有限值扫描对照 |
| expand_weights / noop | 精确 Q8→F64 写入预分配数组 / 共同调用开销控制 |

这些“内核”数字都包含诊断 Job 适配及重复调用框架，不是无调用成本的理想算术周期。旧 A/B 和 r1 裸入口的适配函数在两侧机器码中都各有一次实际内核 CALL，没有发现只给某一侧消掉全部调用的情况。

## 4. 检查、准备与 LTO

ThinLTO 下组件时间，单位 μs/operation：

| --- | --- | --- | --- | --- | --- |

| ffn_gate_up | 2560×960 | 0.353901 | 0.216460 | 521.707571 | 0.000837 |
| ffn_down | 960×2560 | 0.915138 | 0.562614 | 506.947627 | 0.000838 |
| lm_head | 49152×960 | 0.355372 | 0.215982 | 21261.550000 | 0.000831 |

resident 的裸 F32 约 274.5 ns，实际预验证入口约 343.8 ns；独立 activation 扫描约 63.3 ns，与约 69 ns 的入口差额处于同一量级。结合源码，这支持检查在小矩阵上占显著成本。该差额同时包含参数/输出检查、布局和调用组织，独立计时相减不能精确分摊各指令成本；大形状的细小差额甚至受测量波动影响而变号。

`prevalidated` 并非完全免检查：它仍扫描本次 activation 并检查结果。checked 入口另有 scale 检查，ON 吞吐配对变化约 −1.70%～−3.45%。这不是允许绕过 binder 信任边界的理由。

实际准备函数在同一循环中有限值检查、F32→F64 转换及 scratch 写入；消费内核没有再次完整扫描 activation。ON 时 C=960 的准备约 0.353～0.355 μs，C=2560 约 0.915 μs；单消费总时间最小约 117 μs，准备只是其中的小部分。

本批没有显示 ThinLTO 导致普遍 GEMV 回退：实际单消费模型形状 ON/OFF 配对变化约 +0.19%～+0.89%，F32 及已准备入口的小变化有正有负。四个诊断算术主循环（旧 A、旧 B、r1 裸 F32、r1 裸 prepared）各自跨 OFF/ON 的循环编码字节完全相同；函数外围布局仍有差异。

`prepare_only` 的模型形状 ON/OFF 吞吐提升约 24%～29%，但不能全归为省一次 CALL。目标代码确认 ON 将准备内联进诊断入口，消除了已知相等尺寸的部分检查，并改变了循环布局；两侧仍使用逐元素检查/转换/写入的标量循环。本批未单独隔离内联、检查简化和布局的周期贡献。其绝对时间差仅约 0.085～0.256 μs，不能解释数百微秒到数毫秒的 GEMV 主体差距，也不证明运行时的每个准备调用点有相同幅度的 LTO 收益。

旧 A 与 r1 裸 F32 主循环均 97 条/500 B，但寄存器分配、部分指令调度不同，字节并不相同。两者各有 16 条 `vpmovsxbd`、16 条 `vcvtdq2pd`、8 条 activation `vcvtps2pd`，同为 32 条 `vmulpd`、16 条 `vaddpd`。

prepared 去掉 8 条 activation `vcvtps2pd`，改为 8 条 F64 `vmovupd`，权重的 16+16 条转换保持不变。B 删除的是这 32 条权重转换；其 F64 权重读取参与内存源乘法，仍保留 activation 转换及 scale 乘法。静态指令总数与这些访问事实不等于周期或端口占用测量。

上述主循环均无 CALL、FMA、EVEX。预验证及诊断主循环均无栈访问；checked 的一处栈读取是整数循环边界比较，OFF `cmp [rbp-0x50],rdi`，ON `cmp [rbp-0x78],r9`，没有证据将其称为浮点累加器 spill。函数序言/尾声的寄存器保存不计入这个主循环结论。

调用链仍有正常成本：实际 prepared 行 wrapper 两侧均向内部 RowPair 实体调用一次；OFF 的 prepared_total 调用准备和消费者各一次，prepared_dual 调用准备一次及消费者两次。ON 准备内联，total 仍调用消费者一次，dual 两次。没有发现每消费者重新准备的情况。r1 F32 的偶数行路径没有额外内部 GEMV CALL；OFF 函数中的奇数行 fallback 调用不由本批偶数行性能形状执行。

非 LTO 的 `rb1_repeat` 在两侧均保留 `call r14`、状态判断、次数递减及回边；自测也检查重复调用数。计时工作未被整体提升或消除。`noop` 约 0.83～0.85 ns/op 只是控制样本，没有从全部结果中机械扣除。

表示扩大伴随较大形状上的反转，支持“权重预展开收益取决于工作集和访问成本”的解释。当前没有 PMU 或真实带宽数据，尚不能把损失精确拆成某级缓存、TLB 或 DRAM；不能声称每次访问的缓存层级已证明，也不能用模型文件大小×tok/s 代替带宽测量。

## 7. 已确认问题、修复与尚未解决项

| 对象 | 本批证据与状态 |
| --- | --- |
| 原 RB1 校准失败 | 本次确实记录了 qkv/noop 的 8 次及 O/noop 的 1、8 次探针 `elapsed_ticks=0`，同时 status=0、CPU=4。C1 允许校准零区间扩大迭代数，正式样本仍严格拒绝零时长；整批完成。旧失败文件停在 qkv 的 expand_weights 之后，与下一 noop 相符；旧通用错误缺少字段，不能宣称旧失败的具体分支有逐字段原始证明。 |
| C1 resume 清单失败 | 两侧旧源清单均 23 条 binary marker 记录，H1 归一化后选出 17 条适用记录。原先把第二字段当裸路径会漏掉前导 `*`；此次修复路径已实际走通，并继续完成源、对象、配置核对与构建。 |
| 运行时构建/数据流缺陷 | 本批没有确认需要修复的额外 Q8 热循环成本；复用源码检查排除了 gate/up 重复准备及 prepared activation 重扫。没有修改运行时、冻结参考、scale 算术或累加树。 |
| 亚百分比 Q8 差异与 prepare_only 的 LTO 分项 | 保留每轮原值和机器码事实，不把小差异归为某一条指令。若具体后续决策确实依赖它，需要只改变调用/布局的隔离对照；当前数据不足以分摊独占周期。 |
| B 在大形状的精确硬件原因 | 已确认净收益反转及存储/访问范围变化；缓存/TLB/DRAM 的精确贡献未知。只有在考虑相应生产表示时，才需要有边界的计数器与容量/准备验证。 |
| 外层 forward 与整模型速度差 | 此工具调用真实 r1 GEMV 入口，但不包含 AICoreEngine 路由、attention、归一化、完整模型权重流或真实 decode。它不能证明外层组织不存在其他成本，也没有解释同机约 9 tok/s 与 llama-bench 约 52 tok/s 的全部差距。 |

诊断 C1/H1 两个问题已经获得目标运行证据，它们不是 GEMV 运行时缺陷。本轮没有新增运行时修复候选或“候选获得加速”的晋升结论；也没有用本工具的 PASS 替代正式数值路径改动所需的运行时/模型测试。

## 8. 对后续架构的影响与接续边界

准备/消费分层有实际价值，但必须按真实消费者数计账。现有源码中 QKV 是一次打包 GEMV，gate/up 一次准备两次消费；其他输入来自不同计算步骤。不得将准备费用摊到并不存在的整层共享上。按已确认源码，L 层正常路径是 5L+1 次 GEMV、4L+1 次 prepared 准备；这是数据流计数，不是本批 decode 实测。

预验证 scale 边界、activation 有限值检查、失败失效、scratch 生命周期、MXCSR 及完整输出行所有权仍应保留。小矩阵单消费变慢说明未来接口要允许按形状和实际复用评估准备策略，不能把一次准备天然更快写成前提。本批没有足够的形状交叉点数据据此添加运行时切换阈值。

权重表示和 activation 准备是两个不同的成本问题；旧 B 保留为有效诊断对照，尚不构成整模型 F64 物化的生产方案。没有发现应先修复的共享 Q8 热循环缺陷，并不等于可以把所有当前执行组织冻结后直接进入整数阶段。本轮不实施 W8A8/VNNI 或多核。

本批同口径 GEMV 工作单元已完成，无需重复运行相同批次。如果后续继续追踪整模型差距，最小的新增观察应是在同一 Windows decode 窗口记录各 GEMV 的形状、调用数、prepare/consume 时间和窗口总时间，用于判断额外成本究竟在 GEMV 内还是外层。那将是一项独立、受计时扰动约束的观察，不能用当前合成形状的中位数简单相加后宣称已经取得真实 forward 分解。

## 9. 证据索引与复算

- `analysis.json` / `analysis.md`：原比较器分析脚本的完整结果，保留所有轮次。
- `tables/`：两种 LTO 的全部绝对时间、配对变化、有效工作量、归一化与独立统计复算记录。
- `code-evidence/`：符号/函数范围、主循环及调用摘录、PDB/EXE 对应记录和指令字节核对。完整 EXE/PDB/反汇编仍在用户原报告包中。
- `raw/`：本分析包只摘录报告、样本、构建命令、检查记录及相关源码；不是完整目标归档，也不是新安装包。
- `integrity.json` / `current-correspondence.json`：本批输入身份和清单结果。
- `extract_code_evidence.py`：从完整原报告解包目录中的 EXE/PDB/反汇编提取；标准库解析此批 MSF7/PE64，非通用 PDB 工具。
