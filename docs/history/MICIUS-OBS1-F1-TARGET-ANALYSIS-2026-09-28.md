## 完整函数观察

下列都是 VTune 估计值。Port 0/1、3+ ports 与 Store utilization 的分母为 Clockticks；Memory Bound 的本批报告值来自顶层 slots 相关估计。不同列不能相加作运行时间分解。

| 形状 / 实现 | Port 0 | Port 1 | 3+ ports 周期 | Store utilization | Memory Bound |
|---|---:|---:|---:|---:|---:|
| resident / E1 | 74.7% | 86.6% | 95.1% | 5.0% | 0.0% |
| resident / S2 | 81.4% | 89.7% | 83.1% | 1.2% | 0.0% |
| FFN gate/up / E1 | 82.0% | 92.4% | 88.3% | 5.3% | 4.6% |
| FFN gate/up / S2 | 73.5% | 83.5% | 82.0% | 0.0% | 5.0% |

两种形状下，E1/S2 的 0-port 周期均显示 0.0%；1-port 周期在 resident 均为 0.0%，FFN 均为 1.0%。没有观察到 S2 广泛执行饥饿的明显信号。**这不排除局部依赖链限制，也不能证明某一端口精确饱和。** 端口较忙与执行资源压力这一解释相容，不能把所有端口事件直接归于权重转换。

存储事件下降与已知去 spill 的静态变化一致。但它没有转化成 S2 的普遍吞吐收益。合理的研究方向是：去掉的存储需求可能没有决定主要吞吐限制；转换和浮点运算仍需消耗执行资源。这是有证据支持的解释方向，尚非唯一因果结论。

## 必须保留的数据质量限制

### 实际事件样本量

| 形状 / 实现 | Clockticks 样本 | Port 0 样本 | Port 1 样本 | Store-data 4/9 样本 | 1-port 周期样本 |
|---|---:|---:|---:|---:|---:|
| resident / E1 | 4357 | 132 | 153 | 20 | 0 |
| resident / S2 | 4455 | 147 | 162 | 6 | 0 |
| FFN gate/up / E1 | 4751 | 158 | 178 | 24 | 2 |
| FFN gate/up / S2 | 4903 | 146 | 166 | 0 | 2 |

相比原父函数自身行，完整函数样本已补齐；但端口、存储、内存停顿事件的样本远少于 clockticks。小百分比变化不具备同等精度。0 个样本不证明事件从未发生；例如 S2 仍须写最终输出，不能把 0.0% Store utilization 写成没有存储指令。

### resident/E1 顶层分类内部不一致

其 Retiring、Front-End Bound、Bad Speculation、Back-End Bound 分别为 **76.5%、1.1%、0.0%、35.6%，合计 113.2%**，明显不是舍入误差。

原始事件估计也显示：

- `UOPS_RETIRED.SLOTS` = 38,826,058,239；
- `TOPDOWN.BACKEND_BOUND_SLOTS` = 18,090,005,427；
- `TOPDOWN.SLOTS_P` = 50,760,015,228。

仅前两项之和除以第三项就为 **112.128%**。因此异常已存在于相关事件估计中，不是本地把四项百分比相加时产生。不能自行归一化到 100% 后当作可信成本分解，也不能把 resident/E1 的 Retiring 与 S2 的 55.3% 作精确优劣比较。其余三行顶层合计为 99.9%、100.0%、100.0%；合计正常也不是精度保证。

原采集均为 27 个 mux 组，进程级 MUX Reliability 为 0.990 / 0.998。Intel 明确说明高 MUX 值不保证硬件指标准确。本批异常与采样/复用估计的限制相容，具体误差来源尚未分离；不预设是某个内核、CPU 或 VTune 实现缺陷。

另外，single、rotate32、校准与检查仍混在同一函数采样中；两侧报告平均频率与校准工作量也并非完全相同。本轮不由事件总数、CPI 或 CPU Time 推算新的配对性能收益，不外推真实 decode 或 DRAM GB/s。
