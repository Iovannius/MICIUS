## 构建与机器码

实际工具链仍为 MSYS2 Clang 22.1.8、CMake 4.4.2、Ninja 1.13.2。三种配置共同为 O3/native/ThinLTO、r1 prepared activation、row-pair、prevalidated scales、attention value/time-quad；compact/query-F64-cache/fast-math/ITT OFF。

每配置四个关键编译单元共 12 条 compile_commands 与 verbose build 中执行的命令相符；核对时仅规范化路径分隔符、Ninja 序号及依赖文件输出参数。必要 GEMV/权重准备单元有 `-fno-fast-math -ffp-contract=off`，没有将该规则扩展成整个 forward 无 FMA。

Windows F32 预验证主循环没有 Linux GCC 中四个临时权重向量的栈往返。不能再以修复那个 GCC spill 作为本批 Windows 降速的解释或收益承诺。

## 数据解释的边界

明确事实：额外快照从 PW1 的 8 倍 raw Q8 容量降至 4 倍，Q8 消费的两级转换变为一条 F32→F64 转换，但真实 decode 仍变慢。更少静态指令没有转化成本批净加速。

PW1 各自同批基线下的配对结果为 QKV −11.3643%、O −7.1581%；PW2 对应为 −3.4011%、−2.2120%。这是不同批次中的回退幅度描述，不能把它们的差直接作为“F32 相对 F64 的已测加速”。本次 NONE 18.903289 也不能直接与历史 19.4846025 或更早约 9.4 tok/s 比较归因。

PW2 仍把所选权重的消费数据扩大为 4 倍，且保留原 Q8。结合 A1 既有轮转结果，工作集与访问代价仍是有根据的解释方向。但本批没有单独测 F32 内核的单矩阵/轮转成本，也没有 PMU；不能将 −3.4%/−2.2% 定量分摊给缓存、TLB、DRAM、转换执行端或外层调用组织，更不能据此宣称所有紧凑预转换方案均无效。

后两轮整体吞吐较低，O 第六轮降幅较大；全部保留，六轮的胜负方向仍一致。没有频率/温度记录，不将变化硬归因为热或功耗。

## 尚未解决及下一项观察

本次没有确认新的运行时实现缺陷。已排除本候选目标热循环中的额外 spill、CALL、意外 FMA，以及把一次准备误计入 decode 的解释；尚未分离 F32 消费本体与多层工作集/访问组织的成本。

下一项最小观察应复用现有 A1：加入本次 F32 消费入口，与同批 Q8 在相同输入和调用边界下比较单矩阵及 32 矩阵轮转，沿用 QKV/O 两个形状，准备成本另列。它用来区分“F32 本体已经不合算”与“本体有收益但轮转后丢失”；不重复本批 tg128 来追正收益，也不重新开发整套工具。本轮只完成结果分析与边界记录，尚未生成或运行该扩展。

进入下一轮候选前，还需明确它能覆盖的实际 decode 成本比例，避免把局部改进当作全模型目标的充分条件。若只改变耗时占比 p 的部分，即便将其完全消除，总加速上限也是 1/(1−p)；约 +66% 的端到端提升需要 p 至少约 39.8%，有限加速需要更高覆盖。当前没有这份同版本成本占比测量，不能用静态权重数量代替它。

用户要求的接近原始驻留实验量级的实际模型收益目标保留，但仍未达成，也未由现有数据证明可达。不将本候选失败写成整个 F64 阶段完成，不自动进入 INT8/VNNI。
