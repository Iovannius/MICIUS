# I22 · 加载器描述符生命周期

**采用。** 绑定后释放 172.5 MiB 的加载器描述符请求载荷，私有提交量实降约 166.75 MiB。吞吐变化 −0.05625%，生命周期峰值大体持平。

逐阶段分离加载峰值、加载后提交量与 Working Set。只释放引擎已有独立副本且 Shell 确认拥有的 scale。历史对手内存差额不能全部定义为冗余。

### I22 内存分类、所有权与测量边界

来源 `MICIUS-INT8-I22/docs/MEMORY-OWNERSHIP.zh-CN.md`。

以下是固定 SmolLM2-360M Q8_0、I19 接受配置的源码与 GGUF 元数据核算。它没有执行真实模型，也不是新的进程实测。精确张量目录和字节数在 `MODEL-LEDGER.json`。

| 类别 | 请求有效载荷 MiB | 所有权与生命周期 | I22 处理 |
|---|---:|---|---|
| GGUF 原件 | 文件约 368.50；张量有效载荷约 366.80 | 解析器只读文件映射，保留到卸载；F32 norm 与元数据依赖它 | 保留；不计入下列私有申请合计 |
| 解包后 Q8 权重 | 345.00 | Shell 分配，引擎借用；tied embedding 也提供输出权重 | 保留 |

| 引擎私有 scale 描述符 | 172.50 | V1 绑定事务建立独立数组，引擎销毁时释放 | 保留 |
| F32 embedding | 180.00 | Shell 分配，解码阶段借用 | 保留 |
| Packed QKV 权重与描述符 | 46.875 +23.4375 | 引擎额外准备；原权重及私有 scale 仍保留 | 保留，不把潜在别项优化混入本轮 |
| F32 K/V cache | 640.00 | 容量 8192，32 层、KV 维度 320、K/V 两份；初始化触及容量 | 保留；2048 位置逻辑使用量为 160 MiB |
| RoPE 两张 F32 表 | 4.00 | cos/sin 各 8192×64 | 保留 |
| activation / scratch | 约 0.356 | 单步向量及 I19 四份 score 容量等 | 保留 |

以上主要私有申请合计 **1661645184 字节，约 1584.67 MiB**。早期草算约 1583 MiB 少计了一张 2 MiB 的 RoPE 表，已在交付前修正。该修正不改变 172.5 MiB 候选释放量。

合计尚不包括容器、字符串、元数据对象、分配器元数据/对齐/分页、运行库、线程栈等。不能拿它与另一次运行的 Peak Commit 相减后，把残差强行归入某一个类别。私有请求字节也不是所有时刻的 OS Commit：分配器可能保留已释放页。

GGUF 使用 `CreateFileMapping(PAGE_READONLY)` 和 `MapViewOfFile(FILE_MAP_READ)`，未发现加载器另外保存整份原始 GGUF 的私有缓冲。映射仍在并不等于映射全文件都物理驻留，也不等于同样字节数的 Private Commit。Q8 解包权重和 F32 embedding 确实是单独申请，不应被误称为“第二份原始 GGUF”。

公共描述符释放的依据是 `micius_runtime.cpp` 的 V1 绑定：先验证公共 scale，创建独立 `QuantDescriptor[]`，向内部绑定传递独立数组，并转移其所有权；原始 Q8 和 F32 指针仍借用。候选只在绑定成功之后释放公共 scale，先验证所有权集合，再从 `managed_buffers` 移除，避免卸载时重复释放。失败绑定沿用原清理流程。合成检查覆盖 tied/untied Q8 embedding、F32 embedding、不同 head 形状、重置、八轮加载/释放及非法 scale。

llama.cpp 使用冻结源码、`use_mmap=true`、CPU-only、F32 KV、ctx=8192，允许既有 repacking。其 GGUF 映射、后端重排缓冲、KV、图/工作缓冲与 MICIUS 的组织不同。本轮保留完整加载日志，观察 model load、context ready、warmup/reset、四个解码边界及释放后的进程指标；仅凭进程指标仍不能逐页证明每一类物理归属。

| 指标 | 本包字段/来源 | 可以说明什么 |
|---|---|---|
| 当前私有提交量 | `private_commit_bytes`，PSAPI `PrivateUsage` | 此阶段私有提交规模 |
| 生命周期峰值 | 阶段 `PeakPagefileUsage`；正式子进程 Job `PeakProcessMemoryUsed` | 整个加载/预热/解码生命周期的峰值，不能定位是哪一阶段的分配 |
| 当前/峰值 Working Set | `WorkingSetSize` / `PeakWorkingSetSize` | 驻留物理页面，可能包含共享/文件映射页面 |
| 虚拟映射范围 | `VirtualQuery` 的 MEM_COMMIT 按 PRIVATE/MAPPED/IMAGE 分类与 RESERVE 范围 | 地址空间范围；不代表物理驻留，也不等于 PrivateUsage |
| 请求载荷 | 源码公式和加载器逐分配 ledger | 应用申请的有效字节；不包括 malloc 额外空间和 OS 取整 |

Windows 指标定义依据：[进程计数器](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex)、[Job 扩展限制及峰值](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)、[VirtualQuery](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualquery)。复制写入的映射页仍可报告 MEM_MAPPED/MEM_IMAGE，不能直接用区域类型推导页面是否共享。

分阶段观察只在完整输出校验进程启用。观察包含同步 OS 查询和写日志，会扰动资源轨迹；不把这些进程的耗时作为正式吞吐。两引擎的 `after_load` 均代表其模型/上下文准备完成，但内部惰性准备时机不同，因此还必须看预热后与解码后。`after_release` 仍是活进程，输出向量、运行库及分配器缓存可能保留，不能据非零值判泄漏。

正式计时只比较原 I19 和 I22，继承相同输入、数学、ROI 和固定顺序。描述符释放发生在峰值可能已经出现之后，本轮不设“峰值必须下降”目标；也不把 I21 两引擎约 885 MiB 的峰值差额全部当成可回收冗余。

### I22 用户运行结果复核

来源 `reports/I22-review-20261026-141956-192d52cd/I22-RESULTS-REVIEW.zh-CN.md`。

复核日期：2026-10-26。运行标识：`i22-20261026-141956-192d52cd`。

**结论：本轮比较有效，I22 通过预先固定的内存收益与性能非退化门槛，具备进入下一研发基线的条件。** 加载后和 2048 步解码后的私有提交量均减少约 **166.75 MiB（10.47%）**；总体配对吞吐变化为 **−0.05625%**，本轮可视为基本持平。整个进程生命周期的提交峰值基本未变。这符合候选在绑定完成后释放暂存描述符的设计。

本次仅复核已有证据，没有重新运行真实模型，没有修改原始结果、归档或已交付实验包。I22 尚未自动替代已接受的 I19 研发基线，稳定产品 v0.6 及核心目录保持原状。

#### 1. 复核范围与结果

- 交付清单、已安装包的完整文件集合及散列、模型与两篇固定输入、冻结协议与运行配置均一致。候选源码及共享编译单元参数符合交付合同；候选私有开关只作用于 Shell。五个执行入口的程序身份及其已封存反汇编匹配，反汇编未检出 VNNI。
- 六条完整输出，共 12,288 行、603,979,776 个 logits，均复现各自历史输出。I22 与 I19 两篇完整 logits 直接按字节比较一致；各行有限值、argmax、目标词位置和 NLL 均已复算，末行输出亦一致。这里的跨引擎要求是各自复现历史，并未要求 MICIUS 与 llama.cpp 逐字节相同。
- 24 条正式计时的样本集合、顺序、退出码、程序参数、预测输出、分区时间和峰值记录齐全。没有删除慢样本、重试或混入其他轮次。106 项事件的散列链与运行顺序闭合，运行器实际退出码为 0。电源、时钟和进程快照检查通过；快照检查本身不等同于对所有外部负载的连续监控。
- 每篇、每个区间的重复计时均保留，最大 max/min 比为 **1.032845**，低于预设 **1.10**。
- 六条资源观察轨迹的阶段顺序、PID、计数器类型、生命周期峰值单调性、加载器分配账本与释放对象一致。分阶段观察位于专用输出校验进程，正式吞吐进程没有启用这些观察。
- REVIEW/FULL 两份 ZIP 的整体 SHA256、成员完整集合、逐成员 SHA256 与 CRC 均通过。FULL 包含全部六份原始 logits；REVIEW 按设计省略这些大文件。原始运行目录的 433 项文件在复核前后散列不变。

复核同时使用已校验的结构检查器与另行编写的数值、配对统计及归档复算。没有把终端上的 `COMPLETE_VALID_COMPARISON` 单独当成结论。

加载器账本确认释放的公共 scale 描述符请求载荷为 **180,879,360 字节，即 172.5 MiB**。原始 Q8 权重、F32 数据和其所有权集合未随之删除；引擎仍持有绑定时建立的独立描述符。I22 自身绑定前后观察到的私有提交下降分别为 166.75000 / 166.76563 MiB，与独立 I19/I22 进程差值相符。

OS 提交量下降约为释放请求载荷的 **96.67%**。剩余约 5.75 MiB 差值不能仅凭这些记录断言全部来自分配器保留：请求载荷、堆管理、分页及其他进程分配的口径并不完全相同。

预设要求为每篇加载后、解码后均减少至少 128 MiB，且至少体现释放载荷的 80%；两者同时满足相当于本模型至少减少 **138 MiB**。本轮四个观察值均超过门槛。

峰值几乎不降是预期现象：引擎完成绑定时，新旧两份描述符仍同时存在；释放发生在此之后，已出现的生命周期峰值不会回落。因此不能把本轮收益表述为“峰值下降 166.75 MiB”，也不能因峰值持平而否定加载后收益。

I22 的解码后 Working Set 也下降约 166.57–166.64 MiB，但该字段包括共享及文件映射驻留页，不能称为“私有物理内存”。Private Commit、生命周期 Peak Commit、Working Set 与 VirtualQuery 映射范围应分别解释；映射范围不等于物理驻留量。

本轮 I22 解码后的 Private Commit 仍比 llama.cpp 高约 **718.43 MiB**。这只是不同存储、分配与映射策略下的进程指标差，不是已经确认可回收的冗余清单。原始 GGUF 是只读文件映射；源码未显示另外保留完整 GGUF 的独立私有缓冲。解包权重、F32 embedding、引擎私有 scale、packed QKV 和 8192 容量的 F32 KV 仍各有用途；其中 KV 请求容量为 640 MiB，2048 位置逻辑使用量为 160 MiB，容量差不能直接等同于本轮可安全回收量。

卸载后两组 MICIUS 进程私有提交均回落到约 1.6–2.1 MiB，支持本轮观察到的释放行为正常；存活进程仍含运行库、输出对象与分配器状态，不能据此证明所有使用场景都不存在泄漏。

#### 5. 当前状态和证据边界

I22 是一次成功的加载器生命周期改进：移除了已确认不再需要的暂存描述符，并实测降低加载后私有提交规模，同时满足数值一致性和性能非退化要求。它没有改变数学内核，也没有证明剩余内存差额全部可回收。

本轮没有正式采集 llama.cpp 吞吐。因此最新正式竞争证据仍是 I21 的 I19 达到冻结 llama.cpp 无 VNNI 吞吐的 **79.5984%**，不能用本轮的微小性能变化更新这一比例。

状态记录为 `CANDIDATE_ACCEPTED_FOR_NEXT_EXPERIMENT`。已接受研发基线仍为 I19；I22 已具备被选为后续研发基线的条件，未自动提升基线、未修改稳定默认、未提交或发布 v0.7。本次没有发现要求重跑本轮验收的缺口。
