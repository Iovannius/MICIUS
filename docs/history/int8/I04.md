### I4 implementation and evidence boundaries

来源 `MICIUS-INT8-I25-P1/micius/docs/INT8_I4_IMPLEMENTATION.md`。

#### Numerical routes

I4 intentionally extends two I3 precision interventions to continuous context. Layer numbers are zero-based. `L31_GU` uses the frozen F64 GEMV for layer 31 gate/up. `L3_L31_FFN` uses it for gate/up/down at layers 3 and 31. All other GEMVs use the unchanged I1 AVX2 preparation/consumption contract. Each selected GEMV consumes its own current trajectory's input; no activation or state is copied from a separate F64 trajectory. `F64_ALL` replaces all GEMVs and is used only as a parity control.

`src/AI/I4MixedPrecision.cpp` owns invocation-local F64 scratch and calls the original prepared-F64 checked/prevalidated entry points. It does not edit the frozen arithmetic or I1 kernels. Shared I1 FFN preparation still runs before gate/up. That extra work and optional route recording preclude a deployment speed claim. The helper is tested against the frozen oracle on 27 row/column shapes, for both checked and prevalidated calls, with input snapshots and output canaries.

The engine assigns layer/operation tags and chooses the build-time policy before each GEMV. A per-caller-thread `RouteAudit` is scoped to one synchronous token invocation. It records only F64 overrides and checks their exact order against a separate explicit expectation: 0 for F64/I1, 2 for `L31_GU`, 6 for `L3_L31_FFN`, and `5 * layers + 1` for `F64_ALL`. Zero for the pure F64 build means no *overrides*, not zero F64 GEMVs. Nested audits, missing or duplicate routes fail. No observer state is stored in the public context or carried across steps.

The private switches default to evaluation OFF and policy NONE. With both disabled, the new evaluator/helper sources are excluded. Mixed precision requires strict I1 AVX2 and I2/I3 OFF. Evaluation permits the accepted strict F64 or I1 AVX2 configurations and rejects conflicting instrumentation. Public headers, ABI and default presets remain unchanged.

#### Teacher forcing and scoring

`src/app/I4Evaluation.cpp` uses existing V1 APIs. It reads a bounded binary token file, resets before each segment, calls `Micius_PrefillTokenV1` with the next gold input, checks sequence length and the selected routes, then copies the last logits and scores the following gold token. The argmax is recorded but never used as the next input. No padding, special-token insertion, sampling or cross-segment cache is involved.

The token file is little-endian: eight-byte magic `MICI4T1\0`, U32 vocabulary size, U32 segment count, then for each segment a U32 ID count and that many U32 IDs. Segments require 2 through `context + 1` IDs, because the final target is not fed. IDs outside the vocabulary, truncation and trailing bytes are rejected before creating output. The output directory must be new.

Scores use stable double-precision log-sum-exp: subtract the maximum, sum exponentials with compensation, then `NLL = max - target_logit + log(sum_exp)`. Nonfinite logits fail. NLL is in nats. Strict FP flags apply to the score/helper/test sources; this does not claim that unrelated forward operations have all FMA disabled. MXCSR control bits must retain RNE with FTZ/DAZ off. No logit clipping, smoothing or temperature is used.

Each evaluation stores `scores.jsonl` (input ID, target ID, position, NLL, target logit, log-sum-exp, top-1, FP controls, route count and raw offset) and `logits.f32` (all F32 vocabulary entries at every scored position). Explicit segment and whole-run completion records, exact sizes and process success are required.

`scripts/analyze_i4.py` recomputes every score independently from the retained F32 data with Python `math.fsum`, validates all IDs, positions, routes, FP controls, segment totals, top-1 values and completion records, and checks agreement with the C++ scores. Score comparison tolerance is `1e-10 * max(1, abs(expected))`. This is independent score reduction over the *same saved runtime logits*, not an independent neural-network implementation.

#### Controls and limits

The target runner constructs seven isolated builds: untouched original BASE, I4-disabled I1, evaluated F64/I1, both mixed policies, and F64_ALL. It checks their compile flags and CTest results, plus rejected configurations. It uses synthetic A/B/A segments to test reset, and the C++ test independently drives `DecodeOneV1` with gold inputs to verify `PrefillTokenV1` logits, including targets different from the greedy prediction.

On the actual model, eight-step repeated-token traces establish BASE/F64/F64_ALL parity, I4-disabled/enabled I1 parity and evaluator/legacy-client parity. Each primary first step for tokens 42 and 1 must match the sealed I3 result bytes. A 32-step natural-text control checks F64_ALL/F64 parity; each primary 32-step prefix must also match its full evaluation's prefix. These controls support continuous integration correctness on the tested paths, not arbitrary models or all context lengths.

Full source identities, the original baseline's complete 119-file set, the predeclared protocol and fixed data are checked before and after execution. Result files receive hashes and remain in the complete result ZIP. Negative tests exercise wrong targets/positions/routes/scores, missing completion/positions, nonfinite/truncated/trailing tensors, invalid token inputs and existing-output rejection.

The text selection is 8 contiguous prefixes of 256 predictions, not the full WikiText-2 benchmark and not a sliding-window evaluation over the whole test split. Its short contexts and included headings affect absolute PPL. The same IDs, resets and scored positions make within-run comparisons meaningful. Absolute PPL must not be compared directly with differently tokenized, windowed or instruction-formatted published scores. The general methodological reference is the [Hugging Face fixed-length-model perplexity documentation](https://huggingface.co/docs/transformers/perplexity).

The fixed screen is declared before target evaluation. Even passing it would only pass this local subset. I4 does not establish general natural-text quality, long-context behavior, sanitizer coverage or deployment performance, and does not authorize stable integration.

### MICIUS I4：固定自然文本 NLL／困惑度结果

**本工作单元已完成。I1、L31_GU、L3_L31_FFN 均通过预先设定的固定子集筛选。整体 NLL 与 F64 很接近；本子集没有显示两项 F64 干预带来平均 NLL 收益。该结果不等于一般自然文本质量验收，也不构成稳定集成决定。**

#### 2. 固定输入与计算口径

目标模型仍是指定的 Q8_0 GGUF，386,404,992 字节，SHA-256 `48ab3034d0dd401fbc721eb1df3217902fee7dab9078992d66431f09b7750201`。没有下载或替换模型权重。

语料为 [Salesforce WikiText 的 wikitext-2-raw-v1 test](https://huggingface.co/datasets/Salesforce/wikitext/tree/b08601e04326c79dfdd32d625aee71d232d685c3)，固定版本 `b08601e04326c79dfdd32d625aee71d232d685c3`。按数据集顺序选取前 8 篇至少含 257 个编码 token 的文章，保留一级标题和源空白、用一个换行连接数据集行，取每篇前 257 个 ID。完整原文、原始 test parquet、行区间和所有 token ID 随包保留。

每段独立 reset；依次输入位置 0–255 的真实 token，评分位置 1–256 的真实目标。首 token 仅提供条件，不参与作为目标的评分；没有跨文章目标、额外 BOS/EOS、padding 或聊天模板。预测结果不会被喂回下一步。256 个预测位置对应最长 256 个输入 token 的上下文，不是长上下文验收。

采用 [SmolLM2 官方分词器资源](https://huggingface.co/HuggingFaceTB/SmolLM2-360M-Instruct/tree/a10cc1512eabd3dde888204e902eca88bddb4951)，固定版本 `a10cc1512eabd3dde888204e902eca88bddb4951`。已逐项核对 GGUF 内的 49,152 个词表项、48,900 个有序合并规则、17 个特殊 token，以及预处理和特殊 ID；7 个探针及所有入选全文的编码／解码往返通过。还使用 GGUF 词表和规则重新构造分词器并对照；两者使用同一个 tokenizers 库，不能称为独立分词算法验证。分词器身份一致也不证明 GGUF 权重与该 Hugging Face 仓库权重一致。

固定输入 `tokens.bin` 的 SHA-256 为 `7bf7a2574917f8a20f0fbc53f943b4ac7ea37ea470c6ee9dcaa7f1c999aa75c6`；预设协议的 SHA-256 为 `88f9a26a4ffd6556a0e6169d131d8b90051fbe036871d5af039a30643c6becd8`。准备阶段使用 tokenizers 0.23.3、pyarrow 26.0.0；正式运行和独立评分复算只需要 Python 标准库。

这是一份固定的 8 × 256 子集，绝非完整 WikiText-2 基准成绩。与使用不同 tokenizer、滑动窗口、标题处理或聊天模板的外部 PPL 不能直接比较。[固定长度模型困惑度的计算说明](https://huggingface.co/docs/transformers/perplexity)也强调上下文窗口和计分口径对结果的影响。原始数据卡、署名与许可证见 `data/i4/NOTICE.md`。

#### 4. 本轮实现和新验证

I4 从封存 I3 完整源码包独立派生，父包 SHA-256 `303b4cb3aea514963f847e78ed3666df5eecd502aebb704f0d39571890936795`。209 个父包文件中，仅 3 个既有文件变化：`CMakeLists.txt`、`src/AI/AICoreEngine.cpp`、`src/app/MiciusShell.cpp`；其余 206 个逐字节一致。增加私有连续上下文策略、逐词评估器、专项测试、运行／准备／复算工具和固定输入。

F64 内核、I1 算术、公共头文件与 ABI、preset、原始 v0.6 ZIP 和历史证据均未修改。I4 默认关闭。L31_GU 在零基 layer 31 的 gate/up 使用原 F64；L3_L31_FFN 在 layer 3 和 31 的 gate/up/down 使用原 F64。各 GEMV 消费自己当前轨迹的输入，不从另一条 F64 轨迹替换激活。共享 I1 FFN 准备仍会执行；本轮不是混合精度性能优化或测速。

本轮新验证包括：

- 7 个独立构建的 CTest 全通过：原始 BASE 11 项、I4 关闭的 I1 12 项、F64／I1／两个混合配置／F64_ALL 各 13 项，共 88 项执行；基线文件集合保护另有 11 项测试。
- F64 helper 的 27 种形状、checked/prevalidated 两入口均与冻结 oracle 逐位一致；评分经解析解与 long-double 对照；不同真实目标的逐词喂入与独立 DecodeOne 客户端对照通过。

#### 6. 决策与下一边界

当前可以确认：I1 与两项混合精度策略在这份固定自然文本子集上均满足预设局部筛选；I1 首轮单步数值偏移较大并不意味着这份子集的平均 NLL 同样恶化。两项定点 F64 干预在本轮没有产生平均 NLL 收益，因而没有依据仅凭 I3 的 L2 改善就将它们选为默认路线。

建议下一工作单元以 **I1 为主候选，固定更广的独立文本和更长上下文进行匹配 token 评估**，保留混合配置作为对照，再讨论正式质量准入及相关性能代价。本轮到此结束，不自动扩大为量化方案搜索或稳定集成。一般自然文本质量、长上下文质量与稳定合入仍未验收。

#### 审计发现

**[P2／中优先级] 封存 I4 候选的源码身份检查不会拒绝额外源码。**

位置：`scripts/run_i4_nll.py:122–124`。该分支逐项检查 `I4-MANIFEST.json` 的 `source_files`，但没有要求实际完整文件集合与清单相等。`CMakeLists.txt:301–303` 又递归发现 `src/*.cpp`。因此，封存包解压到带残留 `.cpp` 的目录时，额外源码可被构建系统发现，却不会在封存身份检查处被拒绝。

本次在单独审计目录复制了清单中的源码，直接执行交付脚本该分支的原始 AST。干净副本通过；添加一份仅含注释的额外 `.cpp` 后仍通过。没有编译该副本，没有运行模型，也没有向真实候选目录添加文件。该复现证明的是校验接受了额外源码；没有声称这份注释文件已经改变了模型输出。
