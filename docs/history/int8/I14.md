#### 与 llama.cpp 无 VNNI 的剩余差额

下面的差额均为 MICIUS 减 llama；分母为同一范围的插桩总时间差，正负分项全部保留。差额占比不是自身耗时占比，也不是保证能回收的时间。

|---|---:|---:|---:|---:|
| 矩阵含准备 | +5.707734 | 25.02% | +2.900268 | 17.33% |
| Attention | +16.559350 | 72.59% | +13.553616 | 80.99% |
| 其他及区间余量 | +0.545835 | 2.39% | +0.281969 | 1.68% |

Attention 占总体剩余差额 **72.59%**，占末段剩余差额 **80.99%**。因此，“矩阵组占总体最多”并不等于“下一步继续矩阵一定最划算”。

Value 分组差额为总体 **8.476132 秒**、末段 **6.723721 秒**，大于 Score 的相应差额。但 MICIUS 概率归一化包含在 Value，llama 的 Softmax 边界不同，不能把这个差额全称为纯 Value 加权和内核的劣势。

- total：插桩总差额 22.812919 秒；未插桩差额 22.819216 秒；差额之差 -0.006297 秒。
- 1024-2048：插桩总差额 16.735853 秒；未插桩差额 16.723787 秒；差额之差 +0.012066 秒。

两套总差额接近，支持总体归因；仍不能由此证明每个子阶段的局部探针误差都很小。llama argmax 在 forward 余量内，KV 写入在 layer=-1 汇总；同名阶段并非相同精度、算法或访存合同。

#### 下一工作单元建议

**优先评估 Attention Value64 路径的进一步工程优化，Score64 为后续方向，矩阵消费继续保留为候选。** 依据是 Value 的可观绝对成本及最大细项差额、Attention 对总体与末段差额的主导，而不是只按最大类别或末段微小排名决定。

具体先检查当前 Value64 的数据访问、F32/F64 转换、概率归一化和有效性检查的依赖安排；这些是源码可见的研究点，本轮并未单独测出它们各自的耗时，也没有证明是带宽、缓存或指令吞吐瓶颈。优先尝试保持数值合同的局部调度/检查改写，实际可行性需要小型内核实验确认，再冻结一个独立候选。

保留原时间顺序、F64 FMA 后逐步舍入回 F32、异常输入与回退行为。不因对手更快就改为 F32 累加、重排时间归约或更换量化算法；如确需改变数值算法，应另立精度与质量验收。新候选仍需完整输出等同、无插桩端到端收益、各上下文区间与资源门槛，不预承诺 tok/s 或能消除全部差额。
