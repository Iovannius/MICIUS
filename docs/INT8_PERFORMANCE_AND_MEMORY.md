# 无 VNNI 推理性能与模型内存

在最后一次有效的 I25/I22 同场实验中，四行面板将两篇 2,048 步固定输入的总体吞吐提高了 **18.4635%**。本页按决策时实际测量的对象归并各阶段结果。源码发布的功能验证与目标机研究计时分开记录。

## 同场对手与工作负载

I7-P1 的 2,048 步比较中，I1/F64 的配对速度比为 1.361239×，llama.cpp/I1 为 1.987400×。同次 128 步固定前缀和各自 greedy 的 128 步分别统计。Qwen2.5-1.5B 在该轮只有 llama.cpp 单引擎记录。I21 再以封存 I19 和无 VNNI llama.cpp 同场比较，I19 达到对手吞吐的 **79.5984%**，首段为 89.0804%，末段为 75.9664%。该比例的测量对象止于 I19。[I7-P1](history/int8/I07.md) · [I21](history/int8/I21.md)

I25 的性能证据来自 SmolLM2-360M-Instruct-Q8_0、CPU 4、单核、两篇固定输入，加载和绑定在解码计时区间之外。两篇 I22 的中位吞吐率为 28.0643 和 28.2315 tok/s，I25 为 33.3705 和 33.3961 tok/s。正式速度比使用同篇同轮的配对统计，I25 没有新的 llama.cpp 同场速度比。[I25 数据和门槛](history/int8/I25.md)

## 为什么减少常驻提交，加载峰值仍会上升

I21 观察到 I19 和对手的峰值提交量约为 1,593 和 708 MiB。GGUF 的文件映射、KV 容量、embedding、权重描述符和分配器均会影响进程指标。I22 将这一进程差额拆成不同阶段的可验证所有权。引擎已有独立描述符后，Shell 释放 172.5 MiB 请求载荷，加载后私有提交量实际减少约 166.75 MiB。吞吐变化 −0.05625%，通过非退化门槛。[I22 内存研究](history/int8/I22.md)

I23 的合成矩阵工作集含 161 次消费、129 次输入准备。gate/up 共用输入，候选激活展开计入耗时。逻辑载荷从 517.500 MiB 降为 388.125 MiB，六个配对的中位耗时下降 24.4325%。I24 在真实 I22 模型中测量对应边界，进一步扣除展开、探针和迁移预留，两篇的条件净时间预算为 10.2036% 和 13.0387%。这两步分别支持了布局筛选和投入完整模型的决定。[I23](history/int8/I23.md) · [I24](history/int8/I24.md)
