## 性能比较的方法与解释

吞吐以计时区间内 completed_steps / wall_seconds 为准。装载绑定、权重准备、prompt 与 warmup 的范围应从 runner 协议确认；当前 CF7 decode 指标排除装载和准备，另行报告这些成本。

比较候选时记录每轮配对顺序，交替 A/B 与 B/A，逐对计算 100 × (candidate / base − 1)，再取配对收益的中位数。“两个吞吐中位数之比”与“配对收益中位数”是不同统计量，不应互相替换。

当前用户报告的约 19.8 tok/s 来自降频前的多次观察，没有完整逐次样本，因此只作运行表现记录。热状态、频率和后台干扰会影响跨批次比较；CPU 4 的起止采样一致也不能独立证明整段频率恒定或零干扰。短上下文 128 步的结果也不能代表持续长上下文吞吐。

D1/ITT 等诊断模式有自己的开销和归属规则，不能把诊断轮数值与普通 decode 直接混合。微基准的循环、矩阵轮转、缓冲容量与真实模型的访问顺序不同，也不能按 microbench 百分比换算 tok/s。

## 准备与容量的摊销

将一次性准备成本记为 P 秒，若候选每 token 确有可重复节省 Δt 秒，则简单摊销阈值为 N > P / Δt；其前提是 Δt > 0，且两边采用同一计时口径。若用 load+bind 差额作为一次性成本，应避免再次重复加入其中已经包含的准备时间。

CF7 没有确认正向 decode 节省，因此目前不存在可据本轮数据给出的正向摊销 token 数。仅将准备排除出 ROI 不能消除准备成本，也不能证明更大影子容量可以接受。

payload 字节数应与峰值驻留内存分开。额外影子、保留的 canonical 权重、scale、工作区、模型映射和分配开销不是同一个容量口径。

## 以后何时需要重新验收

只有新的数值实现、布局、生命周期或工具链变化引入具体风险时，才安排相应验证。新候选至少需要检查完整消费、准备摊销、尾部与回退、模型绑定/重绑定/reset/销毁，再在指定真实模型上比较 logits 与端到端成本。

已有结果足以拒绝的候选应归档，未隔离因素写为未知；不为“全部问题必须有单一根因”无限扩展实验。本次只新增文档，不触发这些验收步骤。
